# Agent-proposed manual journal entries

Design for Kit review, 2026-11-15. Build work follows separately. No deployment is authorized by this document.

## Current seam

The MCP `post_journal_entry` tool takes one signed cash-side amount and an `external_account_id`, and may call the ledger primitive before queueing a refusal; `user_confirmed` supplied by the agent grants no authority (`app/tools/journal_tools.py:514-560`, `app/tools/journal_tools.py:642-689`). The pending path requires an exact entity/source/external-account mapping and a resolvable account pair, so a free-standing equity reclass cannot enter it (`app/journal/pending_post.py:101-126`). Its existing payload is a single resolved debit/credit pair (`app/journal/pending_post.py:127-153`).

The ledger primitive resolves one pair from a transaction category and an external account, then writes one journal row with one debit and one credit (`app/journal/posting.py:581-618`, `app/journal/posting.py:688-714`, `app/journal/posting.py:813-865`). `post_correction` is for an already posted row and its cash/category reversal and restatement, not a new reclass (`app/journal/posting.py:1236-1268`, `app/journal/posting.py:1284-1313`). The period guard refuses an effective date on or before the entity's closed `period_end` (`migrations/tenant/versions/0007_closed_period.py:7-10`, `app/journal/posting.py:649-678`).

## Proposed contract and enqueue

Add MCP `propose_manual_journal_entry(workspace_id, entity_id, idempotency_key, effective_date, memo, lines, evidence_links, reasoning_trace, model_version)`. Each line has `account_code`, `side` (`debit` or `credit`), and positive integer `amount_cents`; accept 2 to 50 lines. Return `approval_id`, `pending`, and total debit cents. There is no `user_confirmed`, `force_queue`, category, source, or external account argument. Register through the existing policy-wrapped MCP registration point (`mcp_server.py:95-128`, `mcp_server.py:236-245`).

Before writing anything, require entity-scoped workspace authorization with bookkeeper or higher role, including agent/service identities allowed by normal token and tool policy. Reject malformed dates, blank or overlong memo, duplicate or empty evidence links, zero/negative/non-integer amounts, fewer than one line on either side, unequal totals, and totals above 100,000,000,000 cents. Limit evidence links to HTTPS URLs or scoped internal document identifiers; store references, never fetched content. Reject designated cash or linked bank accounts so this tool remains a non-cash path. The queue operation itself never invokes `post_journal_entry` and never writes `journal_entry`.

Resolve every code against `chart_of_account` for this entity and workspace with `is_active=true`; store the resolved account ID, code, and canonical form. The chart has entity scope, `account_number`, `canonical_form`, and `is_active` (`migrations/tenant/versions/0003_journal_v2.py:55-99`), and canonical form is what journal debit/credit fields store (`app/journal/accounts.py:24-31`). Reject any missing, inactive, or ambiguous code. Check `assert_period_open` before enqueue; a closed date is refused rather than queued (`app/journal/posting.py:935-967`). Repeat account and period checks under the approval transaction so a later deactivation or close cannot be bypassed.

Use a new `approval_queue.subject_type = 'manual_journal_entry_proposal'`, `subject_id = approval_id`, `status = 'pending'`, and `amount = total_debits / 100` in USD. Store a versioned immutable JSON payload with workspace/entity, key, exact ordered lines, resolved accounts, effective date, memo, evidence references, proposer user and agent IDs, reasoning, model version, and canonical request digest. The queue already has a JSONB payload (`migrations/tenant/versions/0006_approval_queue_payload.py:76-94`) and a string subject type (`migrations/tenant/versions/0001_tenant_initial.py:394-404`). Derive a deterministic approval ID from workspace, entity, new subject type, and caller-supplied idempotency key; lock it in the transaction. Exact replay returns the same row/status. Same key with any changed payload, including line order or evidence, returns a conflict. A rejected proposal needs a new key. The current proposal path already uses a deterministic ID, advisory lock, and immutable replay check (`app/journal/pending_post.py:43-72`). Write a proposal `decision_audit` row in the same transaction; a failure rolls back both audit and queue.

## Review and apply

Show this subject in the existing Approvals screen with entity, effective date, memo, each debit and credit line, total, evidence links, proposer, and a clear non-cash label. Add a dedicated versioned payload validator and details component; the current journal details validator only accepts the cash-side version 1 envelope (`web/components/journal-proposal-details.tsx:4-25`, `web/components/journal-proposal-details.tsx:27-50`). The screen already lists non-bank subjects as cards, shows requester identity, and uses `ApprovalActions` for single-item decisions (`web/app/approvals/page.tsx:128-149`, `web/app/approvals/page.tsx:299-305`). Its action calls the existing single-item `/decide` route (`web/components/approval-actions.tsx:36-53`).

For this subject, only an owner or admin with a verified interactive human session may approve or reject. Enforce that on the server after the locked row is loaded, regardless of the route's current generic accountant floor (`app/api/approvals.py:181-245`). Reuse the journal proposal's human-session checks, and also reject PAT, agent, service, and MCP/bulk decisions (`app/api/approvals.py:254-264`, `app/api/approvals.py:316-328`; `app/api/approval_clusters.py:587-591`). The approver must have no agent identity; an agent never decides its own proposal. A verified session establishes application provenance, not physical human review, so agent use of a borrowed human session remains prohibited operationally (`PENDING-JOURNAL-REVIEW.md:11`). The UI's owner/admin `canDecide` is a display aid, not authorization (`web/app/approvals/page.tsx:289-294`). Keep this subject out of skip, unskip, recommendations, and all bulk apply paths.

On approve, hold the queue row lock, validate the immutable envelope and digest, recheck entity scope, line balance, active accounts and identical canonical forms, and recheck the open period. Refuse any changed input and leave the row pending. For a 2-line entry, call `post_journal_entry` once. For more lines, deterministically match debits to credits in original order and call it once per balanced pair, in the same transaction, with `source='manual-agent-approved'`, `source_external_id='<approval_id>:<pair-index>'`, `category='Manual journal'`, and the exact approved account pair. The primitive needs an internal-only explicit-account-pair mode that bypasses cash/category resolution but retains its idempotency, period check, append-only insert, hash chain, and post-attempt log (`app/journal/posting.py:581-678`, `app/journal/posting.py:680-769`). Never make that mode callable through the existing MCP post tool. Pairing rule (Kit, review): walk debits and credits in submitted order with two cursors; each step posts min(remaining debit, remaining credit) cents as one pair and advances whichever side reached zero (both if equal). Example Dr A 10000, Dr B 5000, Cr C 15000 posts A/C 10000 then B/C 5000. The pair list is computed once at enqueue, stored in the immutable payload and shown in Approvals, so the approver sees exactly the rows that will post; apply never recomputes it. The logical approval remains one proposal; record all resulting journal IDs in the approval response/audit. A pair refusal aborts the entire decision transaction. The existing single-item handler already locks, applies, marks status, and audits within one transaction (`app/api/approvals.py:215-245`, `app/api/approvals.py:345-372`).

Set `user_confirmed=True` only after the verified decision, with `posted_by_uc_uid` and `approving_human_uc_uid` set from the authenticated owner/admin and `posted_by_agent_id=None`. Gate the whole proposal on total debits, not each split pair: $1,000 or more always requires the verified human session and never auto-applies, even if every pair is smaller. The current H threshold is 100,000 cents, and the ordinary gate accepts a trusted human attestation (`app/journal/materiality.py:27-38`, `app/journal/materiality.py:76-97`). Reject writes no journal rows; both decisions stamp `decided_by_uc_uid`/`decided_at` and create `decision_audit` rows (`app/api/approvals.py:266-292`, `app/api/approvals.py:345-372`, `app/api/approvals.py:518-533`). Projection must use the new source and all resulting IDs, rather than the current bank source used for the existing post projection (`app/api/approvals.py:486-515`).

## Worked example

For an entity with active equity accounts 3010 and 3000, propose effective date `2026-11-11`, memo `Reclass founder capital within equity`, evidence `https://example.com/evidence/capital-reclass`, and lines `Dr 3010 125000 cents` and `Cr 3000 125000 cents`. Debits equal credits at $1,250, cash does not move, and the proposal waits in Approvals. On owner/admin approval, one `manual-agent-approved` journal row posts Dr 3010 / Cr 3000 for $1,250 and links back through the approval audit. If 3000 is not active for the entity, enqueue refuses. The default template includes 3010 but does not list 3000 among its equity rows, so 3000 must be created and active before this example is submitted (`app/journal/accounts.py:75-79`).
