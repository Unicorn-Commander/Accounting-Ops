## 0. Summary

The control plane (Ops-Center) tells this app when an organization is `active`, `suspended` or `archived` through `PATCH /api/v1/provisioning/workspaces/{id}` (`app/api/provisioning.py:153-167`). The app stores the answer in `public.workspace.control_plane_state` (`migrations/public/versions/0020_provisioning_state.py:16-26`) and does nothing with it. The module docstring says so: "Control-plane state is recorded only. There is no shared HTTP/MCP write gate" (`app/api/provisioning.py:4-7`). Today a suspended organization can post journal entries, approve transactions, issue invoices, launch tax runs, mint invitations and connect bank accounts exactly as an active one.

The design puts the gate in two layers:

1. An application refusal with a clear message, at the three places every request already passes: `resolve_workspace` for HTTP (`app/tenancy.py:455-487`), `authorize_workspace` for MCP (`app/mcp_auth.py:222-313`), and `workspace_session` for workers (`app/workspace_session.py:113-127`). A refused write answers HTTP 409 with code `workspace_read_only`. The verdict for every writing route and tool lives in one registry that a guard test checks against the app's own route list.
2. A database backstop: a statement-level trigger on every `books` table that holds book data, which reads the workspace's state in the same transaction as the write and raises when the state is not `active`. A path that forgets the dependency fails closed. The bookkeeping of a read (audit rows, access logs, sign-in rows) is not under the trigger, so reads, sign-in and the audit trail keep working. Section 4.4 proves this on a scratch PostgreSQL under the runtime role.

The inventory in section 3 has 95 writing HTTP routes, 79 MCP tools (33 of them write), 18 workers, runners and operator scripts, 6 inbound machine rails and 20 writes that happen on sign-in or on a GET. Counts by verdict are in section 3.7. The questions that need a decision are in section 12.

Two inbound money paths are not refused but held. Stripe events that arrive during a suspension are verified, stored and replayed on `active` by a sweep inside the `app` process that does not depend on any worker (section 6.5). Bank and Stripe history that the sync workers did not fetch is walked from a frozen cursor that only advances through fully processed pages (section 6.4). Three things must be true before the gate is switched on in a ring, and section 11 lists them as prerequisites: every payment writer locks the invoice row (a live race on `main` today, fixed in its own lane), the lossless cursor is built, and the receipt worker and reconciler, which write `public` tables outside both gates, skip a stopped workspace on their own.

## 1. Two states, two names

This app already has a column called `status` on `public.workspace`, of enum type `workspace_status` with values `provisioning`, `active`, `suspended`, `archived` (`migrations/public/versions/0001_public_initial.py:33`). In this app `status = 'suspended'` has exactly one meaning: a legal erasure closed the workspace. It is written by one statement, `UPDATE public.workspace SET status = 'suspended'` in `revoke_access` (`app/data_rights/erasure.py:370`), on the admin connection only (the runtime role has no UPDATE grant on that column, `migrations/public/versions/0003_rls_and_runtime_grants.py:89`). It is read by `_resolve_membership`, which requires `w.status = 'active'` (`app/tenancy.py:331-338`), so after an erasure nobody resolves a membership and every request answers 403 "No active membership for this workspace" (`app/tenancy.py:344-348`). The erasure docs call this "the hard access kill" (`docs/DATA-RIGHTS.md`, section "The two tiers").

The control plane's state is a different thing. It means "the organization stopped paying" or "the organization closed its account", and its holder still has rights: to sign in, to read, to export, to erase. That is why migration 0020 gave it its own column instead of reusing the enum (`migrations/public/versions/0020_provisioning_state.py:16-26`).

In this document and in the code the two are never read as one another:

| Column | Writer | Values | Meaning | Reader today |
|---|---|---|---|---|
| `public.workspace.status` | erasure Tier 2 (admin role), provisioning (`scripts/provision_workspace.py:168-171` sets `active`) | `provisioning`, `active`, `suspended`, `archived` | `suspended` = erased and closed; nobody may enter | `_resolve_membership` (`app/tenancy.py:337`), `_workspace_exists` (`app/tenancy.py:533`), `list_my_workspaces` (`app/api/workspaces.py:94`), the sentinel's workspace list (`agents/sentinel/run_sentinel.py:110`, `:123`), the sync workers (`scripts/ebay_sync.py:123`, `scripts/stripe_sync.py:124`) |
| `public.workspace.control_plane_state` | the control plane's PATCH (`app/api/provisioning.py:155-164`, runtime role, column grant `0020_provisioning_state.py:29`) | `active`, `suspended`, `archived` | `suspended` or `archived` = the books are read-only for users; the holder keeps reads, export, erasure | only `workspace_status()` in `app/api/provisioning.py:58-62` |

How they combine:

| `status` | `control_plane_state` | What happens |
|---|---|---|
| `active` | `active` | normal |
| `active` | `suspended` | this design: reads, sign-in, export, erasure work; user writes refused with `workspace_read_only`, state `suspended` |
| `active` | `archived` | same refusals, state `archived`; export and erasure still work; no automatic purge (section 7) |
| `suspended` (erased) | any | unchanged: 403 at membership resolution for everyone; the erasure purger still runs (`scripts/purge_due_erasures.py:238-240` deliberately has no status filter); the control plane's calls still accepted (section 8) |
| `provisioning` | any | unchanged: 403 at membership resolution until provisioning marks `active` |

Vocabulary for the rest of this document: "books state" means `control_plane_state`. "Erased" means `status = 'suspended'`. The error codes differ too: a refused write in a suspended organization says `workspace_read_only`; an erased workspace keeps answering the existing 403. The database backstop uses distinct SQLSTATEs for the two (section 4.4), so a log line can never confuse them.

One place does read one as the other today, on the wire: `workspace_status()` returns `row.status` to the control plane whenever `status != 'active'` (`app/api/provisioning.py:58-62`). After an erasure, `GET /api/v1/provisioning/workspaces/{id}` therefore answers `"status": "suspended"` to Ops-Center, which uses the same word for its own state. This is listed in section 13; it is not fixed here.

A second place now writes the control plane's column by hand. The export and deletion runbook merged in #78 tells an operator to run `UPDATE public.workspace SET status = 'suspended', control_plane_state = 'suspended'` as the owner (`docs/ops/customer-data-export-and-deletion.md:171`) and to read `control_plane_state <> 'suspended'` back as proof that access is closed (`:314`). Under this design `control_plane_state` belongs to Ops-Center and moves only on its PATCH (section 9); `status = 'suspended'` is the erasure's own column and already closes every membership on its own (`app/tenancy.py:337`). Setting both makes an erased workspace indistinguishable from a paying one that stopped, which is the confusion the two columns exist to avoid, and it would make a later PATCH to `active` from Ops-Center look like a reopening. Decision 9 asks that the runbook write `status` only and check `status` only; that is a one-line change to the runbook, not to this design.

## 2. The contract rules that bind this design

The common provisioning contract lives in the Ops-Center repository (`docs/design/2026-11-15-apps-in-onboarding.md`, section D). This sandbox cannot reach that repository. The rules below are quoted from the task statement. Rule 18 was named by the task but not quoted; this design could not read it and does not claim to meet it. The reviewer should check section D for anything rule 18 adds.

Rule 6: "Suspended means read-only, and reads include what a read needs. Sign-in, the audit trail, view counters and other bookkeeping of a read keep working in a suspended or archived workspace; a legal erasure runs in every state; only user writes are refused. One app's write lock made sign-in itself fail."

Rule 7: "The control plane's calls are accepted in every workspace state" (the state PATCH and the member DELETE).

Rule 15, as paraphrased by the task: if Ops-Center is down nothing changes; the state only moves on its PATCH.

The design's own two rules of thumb, derived from rule 6:

- A write that narrows access is not a "user write" in the sense of the rule. Removing a member, revoking a token, cancelling an invitation, deleting a bank credential: these make a stopped organization safer and are allowed in every state. Each one is listed in the inventory with that reason and gets its own test.
- A write that widens access, or changes a figure in the books, or spends money on the organization's behalf (an LLM call, a provider call), is a user write and is refused.

## 4. Where the gate goes

### 4.1 Three places compared

**(a) In `resolve_workspace` and `WorkspaceContext`.** Every workspace-scoped HTTP request already passes `_resolve_membership`, whose single query joins `public.workspace` (`app/tenancy.py:327-343`). Adding `w.control_plane_state` to that SELECT costs nothing: no extra query, no extra round trip. `WorkspaceContext` gains a `books_state` field, and `resolve_workspace` refuses a writing method when the state is not `active`, unless the route is in the registry of allowed writes. The MCP surface resolves membership through the same function (`app/mcp_auth.py:279-281`), so the same field reaches `authorize_workspace`. What (a) cannot cover: routes that never call `resolve_workspace` (the user-scoped routes 50, 54; the webhooks 71, 72; the OAuth callback; the provisioning router); the workers, which have no request at all; and writes hidden behind a GET (G13 to G18). Each of those needs its own line of code, and a forgotten one is an open hole with no alarm.

**(b) At the database.** A trigger on the `books` tables that reads `public.workspace.control_plane_state` for `current_workspace_id()` and raises when it is not `active`. The runtime role cannot get around it: it is `NOSUPERUSER`, not the table owner, cannot `ALTER TABLE` or disable a trigger (`migrations/tenant/versions/0005_rls_and_runtime_grants.py:9-16`), and `session_replication_role` can only be set by a role that was granted it (the erasure docs note this, `docs/DATA-RIGHTS.md`, known gap 2). It covers workers, webhooks, callbacks, GET-side writes, sibling repositories that connect directly, and any route added next month without a verdict. What (b) cannot do: give a readable message (it raises a SQLSTATE), choose by role or by route (it sees a statement, not a caller), or distinguish a legitimate always-allowed write from a forgotten one without help. Erasure Tier 1 updates `books.entity` on the runtime role (`erasure.py:299-306`) and would be refused unless the trigger is told. It also binds the owner role: a data backfill migration or a restore that writes a suspended workspace's rows is refused unless it declares itself (section 4.4, costs).

**(c) In the journal's posting function only.** One `if` at the top of `post_journal_entry` (`app/journal/posting.py:496`) and `_insert_journal_entry` (`:827`) stops money from posting. It covers routes 5, 34 to 37, 43, 72, 83 and the sync workers. It misses everything else in section 3: approvals, chart of accounts, documents, invitations, credentials, tax runs, sentinel actions, draft invoices from the quotes seam (which deliberately never posts, `app/api/quotes_seam.py:170`), and the `invoice` tables that `_post_balanced_row` writes beside the journal (`app/ar/invoicing.py:506`). It also cannot see the state without a query of its own, since the posting function receives a session and ids, not a `WorkspaceContext`.

Per request cost: (a) zero extra queries on the hot path (one more column in an existing SELECT). (b) one primary-key lookup on `public.workspace` per writing statement, inside the same transaction; measured at the noise floor in section 4.4 (0.064 ms per single-row insert on a gated table against 0.062 ms on an ungated one, scratch PostgreSQL 16.2, 2000 rows). (c) one SELECT per post.

Effect on sign-in and on the audit trail (rule 6): (a) touches only writing methods on workspace-scoped routes, so `/api/me/workspaces`, `/api/me`, the MCP middleware and every GET are unchanged; the sign-in writes in section 3.6 are on public tables under no trigger. (b) attaches to a named list of `books` tables, which excludes `decision_audit` and `activity_event`; the proof in 4.4 shows an audit row landing in a suspended workspace while a journal insert is refused in the same session. (c) has no effect on either.

How a worker with no request finds the state: under (a) alone it does not. Under (b) it does not need to: the statement itself is refused. For a clear log line and to skip work (not fetch a provider's history only to be refused), the workers get `workspace_session(..., writes=True)`, which reads the state in the transaction it opens (section 4.2).

### 4.2 The choice: two layers

Layer 1 is (a), extended to MCP and to workers. Layer 2 is (b). (c) is not used: it is a subset of (b) with a worse message.

**Layer 1, HTTP.** `_resolve_membership` returns `control_plane_state` alongside role and slug (`app/tenancy.py:331-349`). `WorkspaceContext` gains `books_state: str`. `resolve_workspace` (`:455-487`) checks, after membership and service scope: if `request.method` is `POST`, `PUT`, `PATCH` or `DELETE` and `books_state != 'active'`, look the route up in `app/security/books_state.py:ROUTE_VERDICTS`, keyed by `(method, request.scope["route"].path)`. Starlette sets `scope["route"]` before dependencies run; verified on FastAPI 0.163 and Starlette 1.10 in a scratch venv, and the project pins FastAPI at or above 0.115 (`pyproject.toml`). A route with verdict `A` or `B` passes. A route with verdict `R`, or with no row at all, is refused with 409 (section 5.1). The dependency raises before the body is validated, so a refused write never reaches a handler and never opens a tenant transaction (verified in the same venv: an invalid body to a suspended workspace answers 409, not 422). `resolve_workspace_for_quotes_seam` builds its own context (`app/api/quotes_seam.py:130-139`) and applies the same check with the seam's error body. `resolve_workspace_for_federation` is read-only by construction (`app/tenancy.py:553-556`) and is unchanged.

The user-scoped and unauthenticated writes get one call each to the same helper, `assert_books_writable(session, workspace_id)`: invitation accept (route 50 and G13) after it loads the invitation's workspace; PAT mint (route 54) for each workspace in `workspace_scope`, if question 3 is decided that way; the two Stripe webhooks (71, 72) once they know the workspace; the eBay callback (G14) once it has verified the state.

**Layer 1, MCP.** `_install_agent_tool_policy` (`mcp_server.py:96-129`) knows the tool's MCP name at registration; it sets a contextvar `current_tool_name` for the duration of the call. `authorize_workspace` (`app/mcp_auth.py:222`) reads it, looks the tool up in `_TOOL_METADATA` (`app/api/discovery.py:61`), and refuses when `read_only` is false and the state is not `active`. An unknown tool is treated as a write (the registry's own fallback already says `read_only: False`, `discovery.py:55-59`). The HTTP mirror routes in `app/api/tools.py` set the same contextvar through their router dependency `bind_http_caller` (`app/mcp_auth.py:60`) with a small path-to-tool map, so a read tool served over POST (routes 82, 89) stays allowed. `create_workspace` has no subject workspace and is exempt by name.

**Layer 1, workers.** `workspace_session(sessionmaker, workspace_id, writes=False)` gains the keyword. With `writes=True`, after `set_workspace_search_path` it runs `SELECT control_plane_state, status FROM public.workspace WHERE id = :wid` in the same transaction and raises `WorkspaceReadOnly(state)` or `WorkspaceErased` or `WorkspaceStateUnknown` before yielding. The sync workers, the sentinel, the stale-run maintenance, the document extraction task and the launch worker open their writing sessions with `writes=True`. Their workspace enumeration also adds `AND control_plane_state = 'active'` next to the existing `status = 'active'` (`scripts/ebay_sync.py:123`, `scripts/stripe_sync.py:124`, `agents/sentinel/run_sentinel.py:110`, `:123`), so no provider is called for a stopped organization. The enumeration filter is an optimization; the session check is the guarantee; the trigger is the backstop.

**Layer 2.** Tenant migration 0033 creates `public.refuse_books_write_unless_active()` and attaches `BEFORE INSERT OR UPDATE OR DELETE ... FOR EACH STATEMENT` to every `books` table in the list below. Statement-level, not row-level: one lookup per statement, and it fires even when zero rows match (proved in 4.4). The function:

1. returns at once when `current_setting('app.books_gate_override', true)` is `erasure` (any role) or `maintenance` (only when `current_user` is not the runtime role);
2. reads `control_plane_state, status` from `public.workspace` where `id = public.current_workspace_id()`;
3. raises SQLSTATE `AO000` `workspace_state_unknown` when no row is found (GUC unset, or an id that names no workspace);
4. raises `AO001` `workspace_suspended` or `AO002` `workspace_archived` on the books state;
5. raises `AO003` `workspace_erased` when `status <> 'active'`;
6. otherwise returns.

The runtime role already has SELECT on `public.workspace` (`0003_rls_and_runtime_grants.py:89`), so the function needs no `SECURITY DEFINER`. Step 5 keeps the two names apart on the wire: an erased workspace is refused with a different code than a suspended one, and the message never says "suspended" for an erasure.

Ungated: `decision_audit` and `activity_event`. Both are already INSERT-only for the runtime role (`0005_rls_and_runtime_grants.py:64-70`), so leaving them open cannot change a figure. If question 1 decides that chat stays open while suspended, `agent_session` and `chat_message` move to the exemption set.

**Later tables.** A migration runs once, so discovery inside 0033 gates only the tables that exist when 0033 runs; a table created by 0034 or later would be open, and nothing would say so. Three things close that:

1. 0033 creates `public.books_gate_attach(target_schema text)` beside the trigger function. It runs the `0026` query against `target_schema`, skips the exemption set, and for every table that has no trigger named `trg_books_gate` issues the `CREATE TRIGGER`. It is idempotent, and it runs as the owner, which owns every table. 0033 calls it once for the schema being migrated.
2. `migrations/tenant/env.py` calls it after `context.run_migrations()` (`env.py:88`), inside the same transaction, on every `alembic upgrade` of every tenant schema. A table that 0034 creates is attached by the upgrade that creates it, and 0034 does not need to know; a table that gains a `workspace_id` column later is attached the same way. A downgrade is not covered; the trigger goes with the table.
3. The guard test `test_every_scoped_books_table_has_gate_trigger` (PostgreSQL tier, section 10) runs the same query against the test schema and asserts `trg_books_gate` on every table not in the exemption set, so a table that reaches the schema by any other path (a raw `CREATE TABLE` in a script, a hand change) fails CI. A second test creates a table with a `workspace_id` column as the owner, calls the attach function the way `env.py` does, and proves an insert into it is refused for a suspended workspace through the runtime role.

An event trigger on `ddl_command_end` would attach without the hook, but creating one needs a superuser. In compose the owner role is the image's bootstrap user (`docker-compose.yml:15`); in production it is assumed not to be a superuser, so the event trigger is not the mechanism and the design does not depend on it. The exemption set lives in one place, the attach function's body, so the migration, the hook and the test cannot disagree about it.

Not gated, by design: every `public` table. The sign-in writes (G1 to G8), the credential access log (G9), the membership audit (G11), the control plane's own PATCH and DELETE (routes 94, 95), the export job record (`setup_progress`), the erasure receipt and the email outbox all live there. The application layer refuses the user writes among them (routes 19, 20, 32, 45, 47, 49, 50, 54, 64, 68, 69); the backstop does not need to. The hold table of section 6.5 is `public` on purpose: a held event must land while the books are frozen.

Five `public` tables are the exception to "the application layer covers public": `worker_runs`, `worker_extractions`, `worker_dedup_index`, `worker_reconcile_runs` and `receipt_transaction_link`. They are created by the sibling repositories' own migrations (`scripts/grant_worker_runtime.sql:10-19`), written by the receipt worker and the reconciler directly, with no request, no `WorkspaceContext` and no GUC, so neither layer sees those writes. Lane 1 ships a second attach function, `public.books_gate_attach_by_row(table_names text[])`, which public migration 0021 calls with the five names and which `scripts/grant_worker_runtime.sql` calls again on every re-run (P3), so a sibling table that appears after 0021 is gated when the grant script is re-run for it. Each call attaches a row-level `BEFORE INSERT OR UPDATE` trigger to every named table that exists and has a `workspace_id` column (checked with `to_regclass` and `information_schema.columns`, the way the grant script guards at `:62`), reading `NEW.workspace_id` instead of the GUC and raising the same SQLSTATEs, and it reports per name whether it attached, skipped for a missing column, or found no table. Whether the columns exist is not knowable from this repository (assumed: each worker is pinned to one workspace by environment, `docker-compose.yml:336`, `:389`, and may not store the id per row). Where the column is absent, or where the sibling connects as the owner (the compose default, `:347`, `:393`), the trigger is no guarantee: it cannot key on a row that names no workspace, and the owner can disable a trigger. That is why the siblings' own state check is a prerequisite of the turn-on (section 11, P1) and not a courtesy, and why the attach function reports which of the five it could and could not gate.

Statement types the backstop blocks: INSERT, UPDATE and DELETE on the gated tables. It does not block SELECT, and it does not fire on TRUNCATE (statement triggers for TRUNCATE are separate, and TRUNCATE is already forbidden on the ledger by `0005_rls_and_runtime_grants.py:198-218` and not granted anywhere). It does not fire under `session_replication_role = 'replica'`, which is exactly how the erasure ledger purge runs (`erasure.py:452`); the purge needs no override.

### 4.3 Reads that lazily insert a default row

Three reads write a default row on first use: `get_or_create_policy` (`app/engagement/policy.py:83-105`), `get_or_create_config` (`agents/sentinel/config.py:139-166`), and the orphan reconcile on the launch preview (`app/api/tax_run_launch.py:277-284`). ## 5. What a person sees

### 5.1 A refused write over HTTP

Status 409 Conflict. Not 403: this app's 403 already means "your role or token scope is short" (`app/tenancy.py:223-248`) or "no active membership" (`:344-348`), and a web tier that treats 403 as a sign-out or a permissions problem would send the person to the wrong fix. 409 says the resource is in a state that does not accept this request, which is the truth. The body keeps `detail` as a plain sentence and puts the named code beside it:

```json
{
  "detail": "This organization is suspended. Its books are read-only until the organization is active again. You can still read, export and sign in.",
  "code": "workspace_read_only",
  "state": "suspended",
  "workspace_id": "2b2f0f2e-5e8e-4c9a-9d0b-6b7c1f0a9e11",
  "allowed": ["read", "export", "sign-in"]
}
```

For an archived organization `state` is `"archived"`, `detail` is "This organization is archived. Its books are read-only. An owner can still read, export and erase them.", and `allowed` is `["read", "export", "erase"]`.

`detail` stays a string on purpose. The web tier has no shared error class; about seventy call sites do `body.detail ?? "HTTP n"` and show the result as text (for example `web/app/coa/coa-editor.tsx:122-123`, `web/app/journal/new/manual-entry-form.tsx:163-164`, `web/components/approval-actions.tsx:50`). An object in `detail` would render there as "[object Object]"; a sentence renders as the sentence, on the day the gate ships, before the web lane lands. New client code reads `code`. The gate raises a `WorkspaceReadOnly` exception from the dependency, and a handler registered in `app/main.py` turns it into this body (FastAPI's `HTTPException` carries only `detail`, so the sibling fields need the handler).

When the application layer did not catch a write and the backstop did, the same handler module maps the SQLSTATEs: `AO001` and `AO002` to the 409 above (state from the code), `AO003` to the existing 403 "No active membership for this workspace", `AO000` to 503 with code `workspace_state_unavailable` and a `Retry-After` header (section 9). The handler logs the route, so a backstop hit is visible as a missed verdict and gets a registry row.

### 5.2 The web tier

The web never reads the books state today: no file under `web/` mentions `control_plane_state`, `suspended` or `archived`, and the `Workspace` type (`web/lib/api.ts:22-31`) has no state field. So the change is one field: `GET /api/me/workspaces` and `GET /api/workspaces/{id}` (`:127-152`) gain `books_state`, and the `Workspace` type gains the same.

One banner, a new `web/components/read-only-banner.tsx` in the style of `web/components/disclaimer-banner.tsx` (a slim, non-dismissible strip under the header), mounted in `web/components/app-shell.tsx` between the header and the disclaimer (`app-shell.tsx:49-50`), where `ctx.activeWorkspace` is already resolved (`:24`). Archived: "This organization is archived. Its books are read-only. You can read and export them." ### 5.3 Agents and MCP callers

`authorize_workspace` raises `PermissionError("workspace_read_only: This organization is suspended; its books are read-only")` the way it raises every other denial (`app/mcp_auth.py:308-311`), so the MCP transport returns a tool error, `isError` true, and the model sees the code and the sentence. ### 5.4 Nothing silently dropped

A refused write is an error to its caller in every case: 409 over HTTP, a tool error over MCP, a raised `WorkspaceReadOnly` inside a worker (logged at WARNING with the workspace id and the state, and counted in the pass summary the way `scripts/stripe_sync.py` already records `last_outcome`). No path returns 200 with a no-op. The one place where a read used to carry a write (G15) keeps returning 200 because the read itself succeeds; the pay link is simply absent, and the response says so with `hosted_pay_url: null`. A held Stripe event answers 202, not 200, with `held: true` and `applied: false` in the body, and leaves a row a person can list; it is deferred, not dropped (section 6.5).

## 6. In flight and in the background

### 6.1 A tax run already running

A specialist run is a subprocess driven from the uvicorn process (`app/api/tax_run_launch.py:590-686`). When the PATCH to `suspended` lands mid-run, the coordinator keeps talking to the LLM (the platform's spend, under the service token), and its MCP tool calls that write (`draft_memo`, `flag_for_cpa_review`, `finish_specialist_run`) are refused at `authorize_workspace`. `execute_run`'s own `db_finish` UPDATE (`:458`) is refused by the backstop. On `active`, `scripts/maintain_stale_specialist_runs.py` marks the stale row `failed` on its next pass (`:81-85`), and a person relaunches. The lane adds one check: `execute_run` reads the books state before spawning and once more before publishing, so a run that starts seconds before a suspension stops early instead of spending an hour.

### 6.2 An import or upload already running

Document upload writes the object, then the `receipt` row, then queues the extraction task (`app/api/documents.py:237`, `:280`, `:416`). A suspension between the response and the task's upsert refuses the upsert (`:566`); the receipt exists without an extraction. On `active`, `scripts/backfill_tax_extractions.py` fills the gap, or the person uploads again. A counterparty import (route 18) is one transaction: the backstop refuses the statement that runs after the PATCH commits and the whole import rolls back with a 409.

### 6.3 Bank and Stripe sync during a suspension

The sync workers skip a suspended workspace before any provider call and before anything is recorded, so `connector_state` keeps its last successful cursor. The skip must come before `_record_sync_outcome` (`scripts/stripe_sync.py:307`, `:363`; `scripts/ebay_sync.py:305`, `:408`), because that function writes `last_sync_at = now()` whenever it runs. The test in section 10 asserts exactly that. History that was not fetched during the suspension is then fetched after `active` from the frozen cursor forward, or, when the workspace was suspended before its first sync ever ran, from the durable floor of section 6.4.

Revision 1 called that catch-up lossless. It is not, for two reasons in the code today, and the reviewer reproduced the loss: 100 of 5,100 balance transactions never posted.

- Stripe. `paginate_balance_transactions` stops after `max_pages` (50 pages of 100, `app/connectors/stripe/client.py:410-434`, called with 50 at `scripts/stripe_sync.py:301-303`) and returns a plain list, so the caller cannot tell a complete window from a capped one. `_record_sync_outcome` then sets `last_sync_at = now()` (`:217-243`, `:363`), and the next pass starts at `last_sync_at` minus one day (`:288-295`). Every balance transaction beyond the 5,000th in a window is never fetched again. The same `now()` lands when the provider call failed (`:304-308`) and when the mapper raised for a row (`:329-333`: the loop continues and the cursor still moves).
- eBay. `list_payouts` truncates to `limit` (200, `app/connectors/ebay/client.py:405-407`, called at `scripts/ebay_sync.py:299-301`); `list_transactions` truncates to 500 per payout and for the loose window (`client.py:443-445`, `ebay_sync.py:318`, `:366`); both also stop at 50 pages (`client.py:401`, `:439`); and `_record_sync_outcome` writes `now()` on success and on failure (`ebay_sync.py:305`, `:408`). The provider's `total`, which the client already reads (`client.py:399`, `:437`), is thrown away.

A suspension makes this worse on purpose: freezing the cursor builds exactly the backlog that the caps cut. So the cursor must be lossless before the gate is turned on in any ring that runs a sync worker. That is prerequisite P2 in section 11, built by lane 3a.

### 6.4 Lossless catch-up: a fixed window, resumable pages, a durable cursor

The rule: the cursor advances only through history that was fetched to the provider's last page and processed without error. Three parts, the same for both workers.

**A fixed window, pinned per chain.** A chain is one window and every pass that works on it. The first pass of a chain pins `window_end` from the clock once and stores it in the cursor; every later pass of the chain reads `window_start` and `window_end` from the cursor and never reads the clock. That is the shape the review of #80 (task 1db65b76) requires, and the shape lane 3a ships for both workers: #80 at `fd00679` still writes `last_sync_at = now()` when a pull was exhausted, so lane 3a lands on #80 as merged after its own fix, not on `fd00679`. `window_start` is `last_sync_at` minus one day when a cursor exists. When none exists, it is the durable floor: `granted_at` in the credential blob minus 30 days. Both blobs carry `granted_at`, stamped at connect in unix seconds (`app/api/stripe_oauth.py:255`, `app/api/ebay_oauth.py:425`), loaded by both credential loaders (`app/connectors/stripe/client.py:95`, `:182`; `app/connectors/ebay/client.py:85`, `:184`) and carried unchanged through the Stripe webhook-secret re-store (`stripe_oauth.py:364-375`). The floor lives in the encrypted blob the worker already decrypts, so no migration and no new column; it survives a suspension of any length, because nothing but a reconnect rewrites it; and a reconnect with a new key is a new history, so moving it then is right. The moving default of 30 days before the pass (`stripe_sync.py:288-293`, `ebay_sync.py:287-291`) is removed from the sync path. A blob with no `granted_at` (the field is optional at `client.py:95`; older rows may lack it) uses `encrypted_at` of its row minus 30 days and logs that it did; that value is reset on every re-store (`app/security/credentials.py:112`), so it is the best available bound, not a durable one, and the log line says so. Decision 10 asks how far back the first window may reach for a credential that was connected long before its worker was enabled; the floor is the recommendation. Stripe gets `created[lt] = window_end` beside `created[gte]`; the client has only `created_gte` today (`client.py:386-407`) and gains `created_lt`. eBay already takes `end_date` (`ebay_sync.py:293`, `client.py:389`, `:425`). A fixed `window_end` is what makes a window resumable: without it, a newest-first walk restarts from new rows on every pass and the oldest rows are never reached.

**Resumable pages.** `paginate_balance_transactions` returns `(rows, complete, resume)` instead of a list: `complete` is true only when the provider answered `has_more = false`; otherwise `resume` is the last id seen, the value `starting_after` already takes (`client.py:432-434`). The eBay helpers return `(rows, complete, next_offset)` with `complete` true only when `offset >= total` from the provider's own `total`; the `limit` truncation at `client.py:405-407` and `:443-445` is removed from the sync path, which pages by `offset` until `total`. Each payout's transaction list is walked to its own `total` before the next payout starts, so a payout with more than 500 transactions is complete.

**A durable cursor.** `connector_state.state` (jsonb, `migrations/tenant/versions/0001_tenant_initial.py:454-459`) gains a `cursor` object: `{"window_start", "window_end", "resume", "failed_ids", "floor"}` (`floor` records which lower bound the first chain used and why, for the log and the operator report; if #80 merges its own key names first, lane 3a keeps those names and the names here are descriptive). `last_sync_at` (`:466`) keeps its meaning, the start of the next window, but changes its writer. `_record_sync_outcome` stops writing `last_sync_at = now()` (`stripe_sync.py:218`, `:243`, and the same two statements in `ebay_sync.py`) and writes only the summary. A separate statement sets `last_sync_at = window_end` and clears `resume`, and it runs only when `complete` was true for every list in the window and `failed_ids` is empty. `last_sync_at` is never written from `now()`: the clock is read once, when a new chain opens, to pin its `window_end`, and that stored value is the only thing `last_sync_at` is ever set from. The rules per pass:

| The pass | What is written | Next pass |
|---|---|---|
| walked every page, every row mapped | `last_sync_at = window_end`, `resume = null` | opens a new chain: `window_start = window_end` minus one day, `window_end` pinned from the clock once |
| hit the page cap | `resume` set, `last_sync_at` unchanged | reopens the same window (`window_start`, `window_end` from `cursor`, not from `now()`) and continues from `resume` |
| provider call failed | the summary only | reopens the same window from the start, or from `resume` if one was stored |
| a row's mapping raised | its id in `failed_ids`; the window is finished; `last_sync_at` unchanged | re-walks the same window; idempotency on `(entity_id, source, source_external_id)` (`app/connectors/stripe/mapper.py:37`, `:400`; `app/connectors/ebay/mapper.py:25`, `:392`) posts nothing twice |
| the same `failed_ids` three passes running | an ERROR log line with the ids; the window stays | a person fixes the cause; the next clean pass advances |

The cursor is written in the same transaction as the rows it describes, so a crash between the two cannot claim history that was not posted. The one-day lookback (`stripe_sync.py:288-295`, `ebay_sync.py:288-292`) stays, for rows the provider adds late with an older timestamp; it is not the mechanism that recovers a backlog. The floor is not either: it decides only where the very first chain of a connector starts.

Catch-up after a long suspension: one window per pass, at most 5,000 Stripe rows per pass at the current cap, hourly (`docker-compose.yml:550`). A suspension that accumulated N rows catches up in ceil(N / 5,000) passes with nobody touching it; an operator who wants it sooner runs `--once --workspace <id>` repeatedly, as today. How long each provider keeps history is not stated in the code and this design makes no claim about it; lane 5 records it in `docs/OPERATIONS.md` from the provider's documentation, and an organization suspended longer than that window needs a statement import, which is outside this design.

Order and direction: Stripe lists newest first (assumed from the provider's documentation; the code does not state an order and `tests/smoke/test_stripe_client_unit.py:285` checks only the page count). The design does not depend on it: a window is walked with `starting_after` until `has_more` is false, in whatever order the provider returns.

### 6.5 Stripe webhooks: hold, never lose

Two routes receive Stripe events. Route 71 (`POST /api/connectors/stripe/webhook`, `app/api/stripe_oauth.py:717`) verifies against the workspace's own secret and only logs the delivery into `connector_state.state.webhook_log` (`:660-706`), for every event type it verifies, handled or ignored (`:812-834`); the posting happens on the sync pass. Today that log write sits inside a bare `except Exception` that logs a warning and returns (`:707-711`), and the route answers 200 regardless, so under the backstop a refused log write would have been a silent drop, which section 5.4 forbids. Route 72 (`POST /api/stripe/webhook`, `app/api/stripe_webhook.py:23`) verifies against the platform secret and records a Checkout payment on an invoice through `record_payment`, using the Stripe event id as `external_ref` (`:36`, `:58`), on which `record_payment` is idempotent (`app/ar/invoicing.py:1296-1304`).

Revision 1 refused route 72 with 409 and relied on Stripe's retries, then on a person. That loses money. A customer of a suspended organization can still pay an invoice whose Checkout session was created before the suspension: the pay link lives at Stripe (`app/connectors/stripe/checkout.py:60`), the event arrives, Stripe gives up after its retry window, which the code does not state, and nothing in this repository fetches Checkout events afterwards.

Revision 2 freezes posting and holds the event:

1. Both routes verify the signature exactly as today. An unverified request is still 400 in every state.
2. After verification, and before any `books` statement, the route reads the books state of the workspace it resolved (route 71 from the credential match, `:772-799`; route 72 from the event's metadata, `:42`) with `assert_books_writable`. When the state is `active`, the route proceeds as today.
3. When the state is `suspended` or `archived`, or cannot be read, the route inserts one row into `public.stripe_event_hold` and answers 202 Accepted with `{"received": true, "applied": false, "held": true, "code": "workspace_read_only"}`. Stripe treats any 2xx as delivered and stops retrying; the event is now this app's responsibility. The insert is on a `public` table outside the backstop, posts nothing and widens nothing, so it is allowed in every state. `ON CONFLICT (event_id, consumer, workspace_id) DO NOTHING` makes a Stripe retry of a held event to the same consumer a no-op, and nothing else: the other consumer, or another workspace, is its own row (step 4). This is not a refused write answered with a 2xx: nothing was refused, the posting was deferred, and the body says so.
4. The hold row carries only what the replay needs, never the raw payload (route 71's docstring says why: the payload carries customer email and card digits, `:725-726`): a primary key of `(event_id, consumer, workspace_id)`, where `event_id` is the Stripe event id, `consumer` is `checkout` for route 72 or `connect` for route 71, and `workspace_id uuid not null` is the workspace that consumer resolved; then `event_type`, `livemode`, `api_version`, `invoice_id`, `amount_total` and `currency` (Checkout only, from `stripe_webhook.py:41-45` and the session object's `currency`), `event_created` (the event's own timestamp, for `received_date`), `received_at`, `state` (`held`, `replayed`, `applied_noop`, `unresolved`), `attempts int not null default 0`, `claimed_at`, `replayed_at`, `invoice_payment_id`, `error`. `amount_total` is stored as the integer minor units Stripe sends, never a float. Why the consumer is part of the key: Stripe delivers one event to every endpoint subscribed to its type, and the two routes are two endpoints. Route 71 records every event type it verifies, in `HANDLED_EVENTS` or not (`app/api/stripe_oauth.py:812-834`; the set at `:627-638` has no `checkout.session.completed`), so a Checkout event subscribed on both endpoints reaches both routes, in either order. With `event_id` alone as the key, whichever route arrived first owned the row: a `connect` row first meant route 72's insert hit `DO NOTHING`, the invoice id and the amount were never stored, and the replay appended a log line and posted nothing. That is a lost payment answered with a 202. With the consumer in the key, each route holds exactly what it would have done when active and replays exactly that: the `checkout` row posts the payment, the `connect` row appends the log line. The workspace is in the key because the two routes resolve it differently (route 71 by whichever credential verifies the signature, `:772-799`; route 72 from the event's metadata, `stripe_webhook.py:42`), and a disagreement must leave two rows a person can see, not one row in the wrong workspace. The Stripe event id alone stays the payment's `external_ref` (`stripe_webhook.py:58`), and `uq_invoice_payment_invoice_ref` (`migrations/tenant/versions/0019_ar_invoicing.py:476-480`, unique on `(invoice_id, external_ref)`) stays the reason a Checkout payment posts at most once per invoice however many hold rows describe it. `workspace_id` references `public.workspace`; an event whose metadata names a workspace that does not exist is answered 400 with code `unknown_workspace` and logged, not held, because there is no organization to hold it for (today that event reaches `workspace_session` with a schema that does not exist and answers 500, so Stripe retries it forever). Public migration 0021 creates it with `SELECT, INSERT, UPDATE` to the runtime role and no `DELETE`. It holds no PII and no secret, so it needs no row security. The erasure's public cleanup deletes a workspace's rows as the owner; `docs/ops/customer-data-export-and-deletion.md`, section "Public operational cleanup in dependency order", gains one line.
5. Replay. One function, `replay_held_stripe_events(workspace_id)` in `app/connectors/stripe/held_events.py`, has three callers: the background task that route 94 queues when it moves a workspace to `active` (the pattern of `_run_export`, `app/api/data_rights.py:157`); the sweep `sweep_held_stripe_events()` that the `app` lifespan starts as a task whenever `settings.books_state_gate` is on (`app/main.py:91-120`, the pattern of `init_brigade_client` and `_refresh_loop`, `app/security/brigade_client.py:140-160`, `:223-228`: log and sleep on any error, never block startup) and that runs every `AO_HELD_EVENT_SWEEP_INTERVAL_S` seconds, default 300; and `scripts/replay_held_stripe_events.py --once [--workspace <id>]` for an operator. The sweep selects `stripe_event_hold WHERE state = 'held'` joined to `public.workspace WHERE control_plane_state = 'active' AND status = 'active'`, on the runtime role with a bare `SessionLocal()`: the hold table has no row security, so the runtime role sees every workspace's rows without the admin URL the sync workers need for discovery (`scripts/stripe_sync.py:78-106`). It does not read `STRIPE_SYNC_ENABLED`, does not run in the `stripe-sync` service (which exits or idles when ingestion is off, `scripts/stripe_sync.py:422-436`, and which a ring may not run at all), and needs no workspace Stripe credential: the replay never calls Stripe, because the hold row already carries the amount and the invoice (Checkout uses the platform secret, not a workspace credential, `checkout.py:27`). A ring that holds events therefore always replays them, because the process that holds them is the process that replays them. Rows are replayed oldest first by `event_created`, in three steps with their own transactions. Claim: on the `public` table through a bare `SessionLocal()`, one UPDATE sets `claimed_at = now()` and `attempts = attempts + 1` on a row `WHERE state = 'held' AND (claimed_at IS NULL OR claimed_at < now() - interval '10 minutes')`, the candidate chosen with `FOR UPDATE SKIP LOCKED`, and commits at once. The lease is ten minutes, two sweep intervals: two uvicorn workers, or the PATCH's task and the sweep, cannot claim the same row inside the lease, and a crash mid-replay leaves a claimed row that the first sweep after the lease picks up again. Because the claim commits on its own, `attempts` counts every try, including one whose replay rolled back. Replay: inside `workspace_session(..., writes=True)`, which raises and leaves the row `held` if the workspace was suspended again between the claim and the replay. For `checkout`, first `SELECT id FROM invoice_payment WHERE invoice_id = :iid AND external_ref = :event_id`; a hit marks the row `applied_noop`, with `invoice_payment_id` pointing at that payment. No hit: call `record_payment` with `external_ref = event_id`, `received_date` from `event_created` and the memo "Stripe Checkout (held during suspension)", and mark the row `replayed` with the new `invoice_payment_id`. The outcome mark is a statement on `public.stripe_event_hold` in the same transaction as the posting (the tenant session's `search_path` includes `public`, and the runtime role has UPDATE on the table), so the payment and the mark commit together or not at all. For `connect`, append the delivery to `webhook_log` the way `_record_webhook_delivery` does, with the outcome route 71 would have logged (`handled` or `ignored_event_type`), and mark the row `replayed`. Outcome on error: an `InvoiceError` means nothing was written, because `record_payment` raises in the cases below before any statement (`app/ar/invoicing.py:1273-1293`); the replay then repeats the event-id lookup in a fresh transaction, since a payment under the event id may have landed between the pre-check and the call, and a hit is `applied_noop`. Otherwise the row is marked `unresolved` with the message and posts nothing: "already fully paid", "exceeds the remaining balance", a voided invoice, an invoice that no longer exists. `record_payment` raises the first two before it looks for the event reference (`:1289`, `:1291`, then `:1296`), so they do not mean "already applied"; they mean a real payment arrived for an invoice that another payment, under another reference, already filled or partly filled. A held payment of 100 meeting an invoice with 40 left is money the books do not know about, and the row says so until a person decides where it goes. Any other exception rolls the tenant transaction back; a separate committed statement stores the error on the row, which stays `held`; the first sweep after the lease retries it; after five attempts the row becomes `unresolved` with the last error, so a persistent fault is seen rather than retried forever. The event-id pre-check is a classification aid, not the dedup mechanism: the unique index on `(invoice_id, external_ref)`, `record_payment`'s own check and the invoice lock of lane 0 are what prevent a second posting.
6. Manual fallback. An `unresolved` row is listed in the operator report of section 11 with its invoice, amount, event id and reason; nothing in this app resolves it by itself. The person reconciles it: a partial room on the invoice is recorded through route 36 with `external_ref` set to the Stripe event id and the amount that fits, never the Checkout session id; the remainder, or the whole amount when the invoice was full or void, is a refund or a customer credit, which this design does not post and which is recorded the way the organization records any overpayment today. The event id is what route 72 and the replay use as the dedup key, so a hand-recorded payment with the event id and any later replay collapse into one `invoice_payment` row (`invoicing.py:1301-1302`), and the replay marks the row `applied_noop` when it finds it. Marking an `unresolved` row as reconciled is a one-column UPDATE the report documents; the row is never deleted by the runtime role. The web invoice payment form gets a labelled "Stripe event id" field for this case (lane 4).
7. Nothing is dropped and no 200 pretends to have posted: a held event answers 202 with `held: true`; a replayed event posts once; an `unresolved` event is a row a person can see, with the money named. Route 72's own live path answers 200 `applied: false` today for exactly the two answers that now produce `unresolved` (`stripe_webhook.py:63-64`), which drops a real payment with a 2xx; that is section 13, item 26, and not this design.

**Serialization on the invoice is a prerequisite, not part of this design.** `SKIP LOCKED` serializes hold rows; it does not serialize the invoice, and nothing in the replay does. `record_payment` reads the invoice without a lock (`app/ar/invoicing.py:1273-1293`), checks the balance, inserts the payment and recomputes the balance from the payment rows (`:1366-1381`); `void_invoice` reads the invoice and the payment sum without a lock too (`:1411-1440`); only `issue_invoice` locks with `FOR UPDATE` (`:1052-1066`). Two writers on one invoice in two transactions can both read the old balance and both pass: a person on route 36 beside a Checkout event on route 72, two route 36 calls, two replays of two held events for the same invoice run by two sweeps, or a void beside a landing payment. The unique index on `(invoice_id, external_ref)` stops only the same reference twice. That is a live race on `main` today, with or without a suspension, and it is section 13, item 27. The fix is its own lane on `main` (section 11, lane 0): every payment writer locks the invoice row first, `SELECT ... FROM invoice WHERE id = :id FOR UPDATE` at the top of `record_payment` and `void_invoice`, the way `issue_invoice` already does, so every caller of those two functions (routes 35 and 36, the two tools, route 72 and the replay) is serialized per invoice without knowing it. This design adds no lock of its own and does not reorder its steps around the race. Lane 2 depends on lane 0; the two-writer tests below pass only with lane 0 merged and are marked so.

### 6.6 Queued email and the sentinel

`email_outbox` rows carry no `workspace_id` (section 3.4); their only link to a workspace is `related_invitation_id`, set when an invitation is sent (`app/mailer.py:139`, `:153`). The sentinel skips suspended workspaces. The lane makes the sentinel mark actions due during a suspension `skipped_suspended` instead of executing them late; a person re-schedules what still matters.

## 9. Fail direction and caching

If the state cannot be read, a write is refused. In layer 1 the state arrives with the membership row; if the membership query fails, the request fails with 500 as it does today, and no handler runs. The two Stripe webhooks hold the event when the state cannot be read (section 6.5, step 3): for an inbound payment the safe direction is to keep it, not to post it and not to lose it. In `workspace_session(writes=True)`, a failed read raises `WorkspaceStateUnknown`; the worker logs and skips the workspace this pass, and the held-event sweep leaves the row `held` without counting an attempt. In layer 2 a missing row is `AO000`, mapped to 503 `workspace_state_unavailable` with `Retry-After: 30`, so a client retries rather than concluding the write was taken.

If Ops-Center is down nothing changes (rule 15): the state lives in this app's database and moves only when the PATCH arrives (`app/api/provisioning.py:155-164`). No code path in this design calls Ops-Center to ask about the state. The JIT entitlement answers that `ensure_jit_membership` remembers for 60 seconds (`app/api/provisioning.py:193-197`) concern who has a seat, not the books state, and are untouched.

No cache of the state anywhere. Layer 1 reads it with the membership on every request; workers read it in each writing transaction; the backstop reads it per statement in the same transaction as the write, which is the stated preference. The only "stale" window is a transaction that executed its last books statement before the PATCH committed and commits after; its rows were in flight at the moment of suspension and the rule allows them. A worker's in-memory list of workspaces to visit is at most one pass old (one hour for the sync workers, `docker-compose.yml:496`, `:550`; six hours for the sentinel, `:597`), and the per-transaction read refuses the write even if the list is stale.
